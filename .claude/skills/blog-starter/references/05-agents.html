Production par agents spécialisés

Un expert rédacteur par catégorie, un chercheur d'images dédié, et un chef d'orchestre qui répartit le travail. Voici comment 30 articles de test ont été produits en parallèle, en anglais, sous la persona Alex — et le piège qui a failli tout ralentir.

Pourquoi un expert rédacteur par catégorie

Un guide de progression, une actualité et un test ne s'écrivent pas de la même façon : structure, ton, format de sortie diffèrent. Plutôt qu'un rédacteur généraliste qui ferait tout moyennement, on définit un agent spécialiste par catégorie. Chacun connaît son format sur le bout des doigts, produit un frontmatter conforme, et évite le remplissage « contenu IA générique ». C'est la traduction, côté production, du positionnement éditorial du site : « on joue, on teste », une vraie valeur défendable.

Les agents sont définis dans .claude/agents/*.md. Chaque fichier a un frontmatter (name, description, tools, model) suivi d'un prompt système détaillé (rôle, ton, format de sortie, étapes).

Les 4 agents

1 · blogstarter-guide-writer

Rédacteur expert en guides : prise en main, progression, systèmes de jeu, tier lists, builds/méta. Ton direct, structuré, actionnable.

name: blogstarter-guide-writer
tools: Read, Write, WebSearch, WebFetch
model: sonnet

Les trois rédacteurs (guides, news, reviews) partagent le même en-tête d'agent — tools: Read, Write, WebSearch, WebFetch et model: sonnet — seul le rôle/format de sortie change.

  • Sortie : contents/guides/<slug>.md, frontmatter YAML (category: "guides", tier: null ou "S"/"A"… pour une tier list, reading_time: 8), puis 2 à 4 sections ##, listes, conseils, mini-conclusion. Cible ~700–1000 mots.
  • Étapes : lit _images.json (1re image du jeu → cover/cover_alt/cover_source), 1-2 recherches web pour ancrer le guide, puis rédige un guide adapté au type réel du jeu (gacha, 4X, MMO, extraction shooter, sim militaire…).
Règle langue (dans le prompt)

« Tout le contenu de l'article (title, dek, tags, corps, cover_alt) doit être rédigé en ANGLAIS impeccable. Le site BlogStarter est entièrement en anglais. » La persona auteur est Alex.

2 · blogstarter-news-writer

Journaliste expert en actualité : annonces, mises à jour, événements, sorties. Attaque directe (l'info dès la première phrase), paragraphes courts, angle clair, sans hype creuse.

  • Sortie : contents/news/<slug>.md, category: "news", 2 à 3 sections ##, éventuellement une citation ou une liste de nouveautés, phrase de clôture. Cible ~450–700 mots, reading_time: 4.
  • Image : utilise la 2e entrée du jeu dans _images.json (sinon la 1re).
  • Reste factuel : si un détail n'est pas vérifiable, il reste général plutôt que d'inventer des chiffres.

3 · blogstarter-review-writer

Critique expert en tests : avis argumenté, honnête et nuancé, appuyé sur l'expérience de jeu. Ni complaisance, ni démolition gratuite.

  • Sortie : contents/reviews/<slug>.md, category: "reviews", 3 à 4 sections ## (gameplay, contenu/progression, technique/monétisation, pour qui ?), et une conclusion avec verdict et note. Cible ~800–1100 mots, reading_time: 9.
  • Frontmatter enrichi : rating (note /10 à une décimale), verdict (phrase de synthèse), pros (3-4 points forts), cons (2-3 points faibles) — cohérents avec le corps du test.
  • Image : utilise la 3e entrée du jeu dans _images.json (sinon la 1re).

4 · blogstarter-photo-finder

Recherchiste iconographique. Pour chaque jeu, trouve 3 images distinctes exploitables (key art / illustration officielle, capture de gameplay, logo ou artwork) et les enregistre dans contents/_images.json.

  • Méthode : recherches web ciblées (nom du jeu + « key art », « screenshot », « official », « press kit ») ; privilégie des URLs directement chargeables (.jpg/.png/.webp) de sources sérieuses (site officiel, éditeur, presse, Wikimedia) ; évite les vignettes minuscules.
  • Sortie : un JSON indexé par slug de jeu, chaque image portant url, alt (description factuelle en anglais), source et credit.
{
  "slug-du-jeu": [
    { "url": "https://…", "alt": "…", "source": "…", "credit": "…" },
    // … 3 images par jeu
  ]
}
Fallback (photo-finder)

La cible est 3 images fiables par jeu, mais si le photo-finder n'en trouve pas 3 exploitables, la règle est d'en enregistrer au moins 1 plutôt que de bloquer : un article doit toujours pouvoir se rabattre sur une cover valide (les rédacteurs news/reviews retombent d'ailleurs sur la 1re entrée si la leur manque).

Droits d'image

Le champ credit note la provenance : ces images servent de maquette, les droits devront être vérifiés avant une publication réelle.

L'orchestration

Point de méthode central : un sous-agent ne peut pas piloter d'autres sous-agents. C'est donc le main loop qui joue le chef d'orchestre — il lance les agents, les répartit, et séquence le pipeline.

  1. Étape 1 — Images d'abord (photo-finder)Le photo-finder est lancé et écrit contents/_images.json : 3 images par jeu, chaque URL vérifiée HTTP 200. Ce fichier devient la source d'images partagée pour tous les rédacteurs.
  2. Étape 2 — 6 rédacteurs en parallèleUne fois _images.json prêt, 6 rédacteurs travaillent en parallèle : 2 par catégorie (guides, news, reviews), 5 jeux chacun. Chaque rédacteur lit _images.json et écrit contents/<cat>/<slug>.md.

Attribution des images par index : pour éviter que les trois articles d'un même jeu partagent la même image, chaque catégorie pioche une entrée différente du tableau du jeu :

CatégorieIndex dans _images.json
guides0 — 1re image (key art)
news1 — 2e image (screenshot)
reviews2 — 3e image (logo/artwork)
Pipeline

photo-finder → _images.json (bloquant) puis 6 rédacteurs en parallèle qui lisent ce même fichier. Séquencer les images avant la rédaction garantit que chaque article a une cover valide dès sa première écriture. Contenu en anglais, auteur Alex.

Gestion d'erreur d'orchestration

Chaque agent lancé produit son propre log. En cas d'échec (fichier non écrit, frontmatter incomplet, image manquante), on ne relance pas tout le pipeline : on diagnostique via le log de l'agent concerné puis on relance cet agent isolément, avec le même prompt. Les autres rédacteurs, indépendants, ne sont pas affectés.

Le piège : agents non reconnus en cours de session

Piège réel

Les agents personnalisés de .claude/agents/ ne sont pas reconnus s'ils sont créés en cours de session : le registre des agents est chargé au démarrage. Tenter de les invoquer par leur name juste après les avoir écrits échoue.

Contournement appliqué : on lance des agents general-purpose en leur passant exactement le même prompt expert (celui rédigé dans le fichier .md). Le résultat est identique. Bénéfice secondaire : une fois la session suivante démarrée, les fichiers d'agents sont chargés dans le registre et deviennent réutilisables normalement (invocables par leur nom).

Créer les 30 articles de test

Objectif : valider les gabarits et le rendu avec du vrai contenu, pas du lorem ipsum. Volume produit : 10 jeux × 3 catégories = 30 articles (la catégorie setup a été laissée vide au démarrage — le hardware est en réserve).

Ce que ça valide

Trente articles réels dans les trois formats couvrent tous les composants des gabarits : at-a-glance, tier, stats, verdict/note, pros/cons, images dans la prose, tags, temps de lecture. Le détail de ces composants (at-a-glance, tier, pros/cons…) est décrit en Partie 03. Si le rendu tient sur ce jeu de données, il tiendra en production.
