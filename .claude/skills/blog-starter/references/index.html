Le process complet, dans l'ordre exact où il doit être suivi : commencer par le design system, valider les gabarits (article → listing → home), produire le contenu par agents spécialisés, adapter pour Astro, puis déployer sur Cloudflare. Skill Claude Code

Un skill, pas seulement une doc

BlogStarter est un skill Claude Code : vous l'installez, vous le lancez, il pose les questions (niche, catégories, couleurs, auteurs, sujets) puis déroule le process ci-dessous en validant chaque étape visuelle avec vous. Cette documentation est sa base de connaissance.

01

Installer

Copier le dossier du skill dans vos skills Claude Code :

cp -R blog-starter ~/.claude/skills/
02

Lancer

Dans Claude Code, l'invoquer — ou le demander en langage naturel :

/blog-starter
# « crée-moi un blog sur [niche] »
03

Répondre & valider

Le skill recueille votre config, génère le design system et les gabarits, produit le contenu par agents, puis prépare le déploiement — avec des portes de validation 🚦.

À lire d'abord

Méthodologie & principe directeur

Trois idées gouvernent tout le reste. Les intérioriser évite 90 % des erreurs.

01

Le design system d'abord

On ne dessine pas des pages, on dessine un système. Il devient la source de vérité unique : toute page en découle, toute modif y passe d'abord.

02

L'ordre n'est pas négociable

Design system → article → listing → home → contenu → Astro → déploiement. Sauter une étape, c'est reconstruire deux fois.

03

Le contenu est irremplaçable

La technique rend rapide et scalable ; le vécu (on joue, on teste) rend défendable face à l'IA. Les deux ensemble = un actif durable.

Légende
◆ Fondation — bloquant, ne pas sauter● Étape clé○ Détail / bonne pratique

01

Cadrage éditorial

Niche, marque, domaine, catégories.

Lire →
1.1
Choisir la niche
Guides de jeux live-service focalisés ; audience unique, autorité topique, défendabilité E-E-A-T.
1.2
Marque & nom de domaine
.com brandable (BlogStarter), vérification de disponibilité, cohérence avec la niche.

Maximum 5 catégories (ici : Guides · News · Reviews · Setup). Elles structurent nav, silos SEO et contenu.
02

Le Design System — commencer par ça

La fondation. Rien ne se construit avant qu'il soit validé.

Lire →
2.1
Pourquoi démarrer par le design system ◆
Cohérence garantie, zéro dette de recopie, source de vérité unique. Le piège du HTML brut recopié page par page.
2.2
Concept & direction artistique
Un parti pris fort et assumé (« Command HUD » : dark, accent volt unique, formes angulaires). Éviter le générique.
2.3
Les tokens
Couleurs (surfaces, accent signature, sémantiques), typographie, espacements, rayons, formes.
2.4
Les composants (inventaire priorisé)
UI, gaming (tier list, cartes perso, stats), éditorial, monétisation, états/overlays. Priorités 🟢/🟡/⚪.
2.5
La page styleguide navigable
Une vitrine unique de tous les tokens et composants, à faire valider avant d'aller plus loin.
2.6
Bonnes pratiques
Discipline mono-accent, formes signature, lisibilité éditoriale, accessibilité, un seul CSS source.
03

Valider les gabarits (dans l'ordre)

Article → Listing → Home. Toujours à partir du design system.

Lire →
3.1
Page article (single) ◆
Le cœur : lecture + monétisation. Audit UX/UI, module « at-a-glance », pub intégrée sans casser la lecture, E-E-A-T.
3.2
Page listing (archive)
Un template réutilisable pour catégorie / tag / auteur. En-tête d'archive, grille, pub in-feed, pagination.
3.3
Page home
Spotlight à la une, jeux couverts, dernières sections, sidebar tendances, newsletter.
3.4
La règle d'or
Toute modification d'une page se fait d'abord dans le design system, puis se répercute.
04

Modèle de contenu

Comment le contenu est structuré et stocké.

Lire →
4.1
Markdown + frontmatter
Un fichier par article, métadonnées normalisées (title, dek, category, game, cover, rating, tier…).
4.2
Convention d'images WordPress
Chemin wp-content/uploads/AAAA/MM/JJ/ pour la portabilité et des URLs stables.
4.3
Optimisation & métadonnées ◆
Toute image optimisée (WebP/cwebp) et nettoyée de ses métadonnées avant stockage.
05

Production par agents spécialisés

Un expert rédacteur par catégorie + un chercheur d'images.

Lire →
5.1
Pourquoi des agents experts par catégorie
Le rédacteur de guides ≠ celui des news ≠ celui des reviews. Chacun spécialiste de son format.
5.2
Définir les agents
guide-writer, news-writer, review-writer, photo-finder — rôle, outils, format de sortie, langue.
5.3
Orchestration
Le chef d'orchestre répartit et lance les agents en parallèle ; les images via le chercheur dédié.
5.4
Créer les articles de test
10 jeux × 3 catégories = 30 articles, pour valider gabarits et rendu avec du vrai contenu.
06

Adaptation pour Astro

Du HTML validé à l'app Astro sur Cloudflare.

Lire →
6.1
Scaffold
create astro + adapter @astrojs/cloudflare (SSR), config site & bindings.
6.2
Componentiser le design system ◆
Le CSS validé est copié tel quel ; les maquettes deviennent des composants (rendu fidèle au pixel).
6.3
Couche données D1
Schéma (categories, games, authors, articles, tags), Drizzle, migrations.
6.4

6.5
Routes SSR + cache edge
home, /[category], /[category]/[slug] ; Cache-Control s-maxage.
6.6
Médias sur R2
Créatives pub servies via une route /media depuis R2 ; covers en statique.
