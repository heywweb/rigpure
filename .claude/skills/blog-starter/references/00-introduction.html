Introduction & cadrage

Comment utiliser le skill BlogStarter pour dérouler ce process sur votre propre niche, puis pourquoi ce projet existe, quel modèle économique il sert, sur quelle stack il tourne, et ce qu'il faut avoir en main avant d'écrire la première ligne. On pose aussi le principe directeur qui gouverne tout le reste de la doc.

0.0 — Prise en main : le skill BlogStarter

BlogStarter est un skill Claude Code qui génère un blog rapide, monétisé et SEO/GEO-ready (Astro + Cloudflare) à partir d'une simple configuration : niche, catégories, couleurs, auteurs, sujets. Cette documentation est l'implémentation de référence — un média gaming complet — mais le même process s'applique à n'importe quelle niche.

Deux façons de lire cette doc

Soit vous déroulez le process à la main en suivant les 12 parties comme un tutoriel ; soit vous laissez le skill l'orchestrer : il pose les questions, lit la partie de référence adaptée à chaque phase, et valide avec vous avant d'avancer. Les deux chemins mènent au même résultat.

Installer le skill

Copier le dossier blog-starter/ dans un emplacement de skills, puis relancer Claude Code :

# Option A — disponible partout (recommandé)
cp -R blog-starter ~/.claude/skills/

# Option B — pour un projet précis
mkdir -p <votre-projet>/.claude/skills
cp -R blog-starter <votre-projet>/.claude/skills/

Lancer le skill

Dans Claude Code, invoquer la commande — ou simplement formuler la demande en langage naturel :

/blog-starter
# ou : « crée-moi un blog sur [niche] », « nouveau blog »

Le skill enchaîne alors un court questionnaire d'intake, écrit la config, puis déroule les phases en validant les étapes visuelles (design system, gabarits) avec vous.

Le déroulé (phases & portes de validation)

Le skill suit un ordre non négociable et lit la partie de référence correspondante avant chaque phase. Les 🚦 marquent les portes où il s'arrête pour votre validation.

  1. 0 · IntakeRecueillir la config, la valider (max 5 catégories, hex valides…) et écrire blog.config.json.
  2. 1 · Cadrage (réf. 00–01)Confirmer niche, marque et catégories.
  3. 2 · Design system (réf. 02) 🚦Appliquer le thème (preset ou gen-theme.mjs), générer le styleguide, valider.
  4. 3 · Gabarits (réf. 03) 🚦Article → listing → home themés, valider.
  5. 4 · Modèle de contenu (réf. 04)Frontmatter, convention d'images, règle d'optimisation.
  6. 5 · Agents + contenu (réf. 05)Générer les rédacteurs de niche + photo-finder, produire les premiers articles.
  7. 6 · Astro (réf. 06)Scaffold, injection de la config (catégories/marque/auteurs/langue), D1, import.
  8. 7 · SEO/GEO + monétisation (réf. 07–08)Head SEO, JSON-LD, sitemap/robots/ads.txt/llms.txt/RSS, consentement.
  9. 8 · Déploiement (réf. 09–10)Vous exécutez les logins ; D1/R2/KV, build, deploy.

0.1 — Objectif & modèle économique

BlogStarter (votreblog.com) est un blog / média gaming en anglais, articulé autour d'un persona-auteur unique, Alex. L'objectif n'est pas de « faire un site » mais de bâtir un actif média rentable : un flux de contenu de niche capable d'attirer du trafic organique et de le monétiser à la marge la plus large possible.

Le modèle s'inspire directement de Prydwen : des guides denses et tenus à jour pour des jeux live-service (tier lists, builds, reroll, roadmaps de patch). Ce type de contenu génère de la recherche récurrente — chaque patch, chaque nouveau personnage relance la demande — et fidélise une audience qui revient.

Le contenu se répartit en quatre catégories — Guides, News, Reviews et Setup — dont le rôle éditorial et l'articulation en silos sont détaillés en partie 01.

La monétisation combine trois leviers :

  • Display / RSoC (Related Search on Content, style AdSense) : la couche de revenu de base, servie sur chaque page vue.
  • Affiliation : buy box et comparatifs (pilier hardware tenu en réserve : « meilleur X pour jouer à… »).
  • Offres jeux en CPI (coût par installation) : le média gaming se prête naturellement à promouvoir les jeux qu'il couvre.
Le principe économique

La logique est celle de l'ad-arbitrage : « vitesse = marge par visiteur ». Chaque milliseconde de chargement et chaque octet superflu grignotent la marge sur un visiteur payé. Un site rapide, léger, servi au bord du réseau, transforme plus de trafic en revenu net. C'est pour ça que la performance n'est pas une option décorative — c'est le cœur du business.

0.2 — Vue d'ensemble de la stack

Toute la stack a été choisie pour servir ce principe : rendu côté serveur au plus près de l'utilisateur, zéro serveur à gérer, coûts qui restent dans les quotas gratuits au démarrage. Chaque brique a un rôle précis.

BriqueRôlePourquoi elle
AstroFramework de rendu (SSR)Zéro JS par défaut, rendu HTML rapide, s'adapte au bord Cloudflare via l'adaptateur officiel.
Cloudflare WorkersExécution au bord (edge)Le rendu se fait au plus près du visiteur, sans serveur à maintenir.
D1Base de données (SQLite au bord)Stocke le contenu (articles, catégories, jeux, auteurs, tags) et permet des requêtes SQL rapides.
R2Stockage objet (médias)Héberge les créatives publicitaires (WebP), servies via une route dédiée sans frais d'egress.
KVClé-valeur (sessions)Fournit le binding SESSION requis par Astro pour les sessions.

Concrètement : le contenu vit dans D1, les images/créatives dans R2, les sessions dans KV, et Astro assemble le tout en HTML rendu par un Worker, mis en cache au bord. Le détail de chaque brique est traité dans les parties 06 (Astro), 08 (monétisation) et 09 (déploiement).

Piège Astro à connaître dès maintenant

Le projet tourne en Astro ^7.2.6, mais l'API runtime se comporte comme Astro v6 : Astro.locals.runtime.env a été supprimé. L'accès aux bindings (D1, R2, KV) passe désormais par import { env } from 'cloudflare:workers'. Ignorer ce point provoque une erreur 500 au premier run. Détaillé en partie 06.

0.4 — Le principe directeur

Trois idées gouvernent tout le reste de cette documentation. Les intérioriser évite l'écrasante majorité des erreurs.

  1. Le design system est la source de vérité uniqueOn ne dessine pas des pages, on dessine un système. Le fichier styles-v2.css est la référence : toute page en découle, et toute modification d'une page passe d'abord par le design system, puis se répercute. Jamais l'inverse. Ce principe est développé en partie 02.
  2. L'ordre n'est pas négociableDesign system → gabarits (article → listing → home) → contenu → adaptation Astro → déploiement. Sauter une étape, c'est reconstruire deux fois. C'est la raison pour laquelle la partie 02 vient avant tout le reste.
  3. Le contenu est irremplaçableLa technique rend le site rapide et scalable ; le vécu — on joue, on teste, on note — le rend défendable face à l'IA et crédible au regard de l'E-E-A-T. Les deux ensemble forment un actif durable.
À retenir

Cette partie n'écrit aucune ligne de code de site. Elle installe la bonne posture : un objectif business clair (monétiser du trafic gaming à marge maximale), une stack alignée sur cet objectif (rapide, edge, quasi gratuite), et une règle de fer (le design system d'abord). La suite ne fait qu'exécuter ces choix, dans l'ordre.
